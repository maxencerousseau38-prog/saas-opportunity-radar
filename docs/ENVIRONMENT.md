## Local setup

1. Install Node 26.13.0 (for example `nvm install` reads `.nvmrc`).
2. Install pnpm 10.34.9: `npm install -g pnpm@10.34.9`.
3. `pnpm install`
4. Copy the relevant sections of `.env.example` to `apps/web/.env.local` (web) or
   to the worker's environment. Nothing in Sprint 0 requires real values.
5. Database work (from Sprint 1): install Docker and the Supabase CLI 3.0.0, then
   `supabase start` from the repository root.

`engine-strict=true` (`.npmrc`) makes installs fail on another Node major.

## Environment variables

Validated at startup by `@sor/contracts/env`:

- startup fails if any `NEXT_PUBLIC_*` variable name looks like a secret
  (`SECRET`, `SERVICE_ROLE`, `PRIVATE`, `PASSWORD`, `TOKEN`, `*_API_KEY`,
  database URLs);
- error messages contain variable **names only**, never values;
- `apps/web/lib/env.ts` imports `server-only`, so server variables cannot be
  bundled into client code.

| Variable | Used by | Exposure |
|---|---|---|
| `APP_ENV` | web, worker | server |
| `NEXT_PUBLIC_SUPABASE_URL` | web | browser |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | web | browser |
| `SUPABASE_SECRET_KEY` | web (server), worker | server only |
| `SUPABASE_URL` | worker | server |
| `WORKER_ID` | worker | server |
| `AI_PROVIDER` | worker | server — only `fake` until PD-24 chooses a real provider |
| `AUTHOR_HASH_SECRET` | worker | server only — salt of reviewer-identity hashes (32+ characters) |
| `WORKER_CONCURRENCY` | worker | server — jobs processed per polling cycle (default 2) |

Key model verified in Sprint 1: the Supabase CLI 3.0.0 local stack exposes
publishable and secret keys (`sb_publishable_…`, `sb_secret_…`) as well as the
legacy anon/service-role keys. The project uses the publishable/secret pair.

## Database types

`packages/database/src/generated.ts` is generated from the schema:

```bash
supabase gen types typescript --schema public > packages/database/src/generated.ts
```

Run it after every migration. The CI `database` job fails when the committed
file differs from the schema and prints the expected file between markers.
The file is excluded from Prettier and ESLint.

## Supabase project

`supabase/config.toml` was generated by `supabase init` (CLI 3.0.0). Deliberate
change: `[auth] enable_signup = false` (the generated default was `true`);
users are invited (Technical Blueprint §11.1). Migrations and pgTAP tests arrive
in Sprint 1.

## Continuous integration

`.github/workflows/ci.yml` runs on pushes to `main` and `claude/**`, and on pull
requests:

- **checks**: install (frozen lockfile), format check, lint, typecheck, unit tests, build;
- **e2e**: local Supabase stack, labelled demo fixtures, the real worker (fake AI
  provider) and Playwright with Chromium (after `checks`);
- **worker-integration**: local Supabase stack and the worker's integration tests
  (real PGMQ: enrichment, duplicate delivery, crash recovery, retry, cancellation,
  CSV imports);
- **database**: Supabase CLI 3.0.0 local stack, PGMQ verification gate (prints
  `pgmq` version and function signatures), pgTAP, `supabase db lint`, security
  advisors, generated-types drift check.

Running the worker locally (after `supabase start` and the variables above):

```bash
pnpm --filter @sor/worker build
```

```bash
node apps/worker/dist/main.js
```

## Cloud-session constraints

Claude Code cloud sessions may have no Docker daemon (observed 4 Nov 2026): the
database job then runs only in CI. A pre-installed Chromium can be used for E2E
with `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/opt/pw-browsers/chromium pnpm test:e2e`.
