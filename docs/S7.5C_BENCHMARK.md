# S7.5c — catalogue benchmark

**État au 7 novembre 2026 :** la CI du HEAD est verte et la génération/
sérialisation Node a été mesurée deux fois sous Node 26.13.0. Les mesures
PostgreSQL et PostgREST/Supabase n’ont pas pu être exécutées ici, car Docker,
Supabase CLI et les outils PostgreSQL manquent. S7.5c reste donc non validé.
Le harness ne requiert aucun service distant, abonnement ou déploiement.

## Outils retenus

| Besoin | Choix | Compatibilité et performance | Maintenance et licence | Alternatives examinées |
|---|---|---|---|---|
| Générer les 2K/10K/50K lignes | SQL PostgreSQL `generate_series` | Génération set-based dans le moteur; le trigger réel `search_vector` s’exécute pendant l’insertion. Déterministe, sans dataset externe ni trafic réseau. | Intégré à PostgreSQL 17 ciblé par `supabase/config.toml`; licence PostgreSQL permissive. Aucun paquet supplémentaire. | `@faker-js/faker` (MIT, Node compatible) produit des valeurs plus réalistes, mais ajoute une dépendance et du travail CPU côté générateur; ce réalisme ne mesure pas mieux le volume SQL. `@snaplet/seed` (MIT) connaît le schéma et les relations, mais la documentation Supabase le décrit comme communautaire avec des correctifs occasionnels; trop général pour ce seul benchmark synthétique. |
| Charge SQL PostgreSQL | `pgbench` avec scripts SQL personnalisés | Outil PostgreSQL natif qui répète les scripts, simule des connexions concurrentes et donne débit, latence, échecs et latence par instruction. Les scripts appellent la fonction SQL de filtrage du catalogue avec le rôle RLS `authenticated`. | Distribué avec PostgreSQL, aligné sur le serveur 17; licence PostgreSQL. | `k6` est maintenu activement et très adapté à HTTP, mais est sous AGPL-3.0 et ne fournit pas le chemin SQL PostgreSQL recherché sans extension. `autocannon` est adapté à HTTP Node, mais ne remplace pas le client natif PostgreSQL. |
| Couche Node et API Supabase | Node `node:perf_hooks` + `fetch` intégré | Mesure séparément la création/JSON de 2K/10K/50K objets et, lorsque les clés locales sont fournies, la latence du Data API PostgREST avec 1 et 10 requêtes concurrentes. Le test HTTP utilise le JWT local `authenticated`, sans clé service. | API incluse dans le runtime Node du dépôt; pas de licence ou dépendance supplémentaire. Le moteur du dépôt est fixé par `.nvmrc` à Node 26.13.0. | `pg` (node-postgres, MIT, maintenu et compatible Node 26) serait approprié pour des mesures driver directes, mais `pgbench` isole mieux le moteur DB, et le code produit passe par Supabase/PostgREST plutôt que par `pg`. |

Ce choix sépare le coût de génération Node, le filtre SQL avec RLS, et la
surcouche HTTP Supabase. Ces nombres ne sont pas des comparaisons brutes entre
outils: chacun mesure une couche et un travail distincts. Le test PostgREST lit
la table paginée; il ne remplace pas une mesure du parcours API web complet,
qui exige un workspace et une session utilisateur.

## Exécution locale

Prérequis : Node 26.13.0, Docker Desktop en marche et la stack Supabase locale
déjà démarrée. Le runner utilise `SOR_S75C_DOCKER_BIN` si défini, sinon cherche
les emplacements d’installation Windows usuels avant de résoudre `docker` via
le PATH.
Le conteneur doit s’appeler
`supabase_db_saas-opportunity-radar`, utiliser un endpoint Docker Windows local
`npipe://`, et contenir `psql`/`pgbench` version 17. Aucun client PostgreSQL
Windows n’est requis. Le runner refuse `DOCKER_HOST`, un contexte Docker non
local, un autre conteneur, une API non locale ou un port API autre que 54321.
`DOCKER_CONTEXT` reste utilisable si son endpoint est le named pipe local
attendu. Depuis `docker exec`, il joint PostgreSQL par socket Unix
`/var/run/postgresql`, port 5432, base `postgres`, rôle `postgres`; il ne tente
pas de joindre le port hôte 54322 depuis le conteneur.

Avant toute suppression, le runner relève séparément le nombre et l’empreinte
de toutes les colonnes des lignes hors des deux préfixes autorisés. Il exécute
ensuite le nettoyage puis répète immédiatement cette mesure et s’arrête si elle
diffère. Le SQL de nettoyage refuse tout trigger DELETE applicatif activé sur
les deux tables cibles, vérifie les références FK vers les fixtures avant
chaque suppression et échoue dès qu’une ligne dépendante existe; il ne supprime
jamais de lignes dans d’autres tables. Le nettoyage utilise exclusivement les
filtres littéraux `saas_products.slug LIKE 'sorbench-s75c-p-%'` et
`companies.slug LIKE 'sorbench-s75c-co-%'`. Le seed ne nettoie aucune donnée.
Les scripts SQL sont copiés dans un répertoire temporaire versionné par SHA-256
dans le conteneur puis appelés avec leurs chemins conteneur pour `psql -f` et
`pgbench -f`. Un fichier homonyme déjà présent avec un contenu différent fait
échouer le staging plutôt que d’être écrasé. Après chaque copie, le runner relit
le fichier dans le conteneur, compare ses octets au fichier local et recalcule
son SHA-256 avant de poursuivre.

Chaque processus externe est limité à 15 minutes par défaut
(`SOR_S75C_COMMAND_TIMEOUT_MS` permet d’ajuster cette durée, minimum 11 s pour
garder une marge avec le délai interne).
`psql` et `pgbench` ont aussi une limite `timeout` dans le conteneur, avant la
limite du client Docker, afin que couper le client ne laisse pas l’outil SQL
tourner. Un dépassement tue le processus et fait échouer le run. `SIGINT`/`SIGTERM`
empêchent tout nouveau benchmark et annulent les requêtes HTTP. Une commande
SQL déjà attachée à Docker est laissée sous son `timeout` dans le conteneur pour
éviter de tuer seulement le client et de laisser `psql`/`pgbench` actif; après
sa fin ou son délai, le bloc `finally` garde la possibilité d’exécuter le
nettoyage autorisé et son contrôle d’empreinte. L’arrêt peut donc attendre
jusqu’à la limite interne SQL, au maximum 10 secondes de moins que le délai
configuré du client. Les requêtes HTTP locales ont un délai de 10 s.

1. Démarrer la stack locale si nécessaire avec `supabase start` (ne pas utiliser
   `supabase db reset`).
2. Charger les valeurs locales de `supabase status -o env` dans
   `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` et `SUPABASE_JWT_SECRET`. Le
   runner ne lit plus `DATABASE_URL` : les outils PostgreSQL tournent dans le
   conteneur nommé ci-dessus et utilisent son socket local.
3. Depuis la racine, lancer `pnpm benchmark:catalog`.

Le runner recrée successivement les 2K, 10K et 50K entrées, analyse les tables,
puis exécute pour chacune un parcours de page et un parcours de comptage avec
1 puis 10 clients pgbench, 100 transactions par client. Il vérifie le nombre
exact et l’unicité des slugs; un SHA-256 SQL des champs déterministes des 2K
premières lignes doit rester identique aux tailles supérieures. Le précontrôle
PostgREST vérifie le nombre total visible avant 100 requêtes REST (10
échauffement) aux concurrences 1 et 10. Les résultats sont JSON sur stdout.
`--postgres-only` permet d’omettre explicitement PostgREST; la commande
complète exige ses variables locales. Pour les seules mesures Node, lancer
`node scripts/benchmark-catalog.mjs --node-only`.

## Mesures disponibles

Mesures réellement exécutées deux fois le 7 novembre 2026, Windows x64, Node
v26.13.0, 16 processeurs logiques, 33.7 GB de mémoire visible. Le runtime
officiel Windows x64 a été téléchargé dans `%TEMP%` et son SHA-256 comparé à
`SHASUMS256.txt` de Node.js: `dcc60d59a0746999f99064a01c020445d54d84228c691cdbf25b49ac3b59150a`.
Chaque cellule est la médiane de cinq échantillons après un échauffement; le
chronométrage couvre la création des objets synthétiques et leur
`JSON.stringify`, pas le hachage.

Le nombre de lignes, le nombre d’octets et le SHA-256 sont identiques entre les
deux exécutions pour chacune des trois tailles. Les temps varient; ils sont
mesurés séparément par run et ne sont pas fusionnés. Ces résultats ne mesurent
ni insertion PostgreSQL, ni API Supabase, ni code de production.

**Mesures PostgreSQL/PostgREST : aucune.** Aucune commande Docker, aucun SQL et
aucun benchmark n’ont été exécutés pendant la modification du harness. Les
assertions de reproductibilité SQL, visibilité PostgREST, empreintes hors
préfixe, garde-fous FK, staging `docker cp`, invocation par socket et nettoyage
automatique restent à valider lors d’une vraie exécution locale. Les résultats
Node ci-dessus sont antérieurs à ces modifications et ne constituent pas une
validation de celles-ci.

Les fixtures couvrent entreprises, SaaS, trigger de recherche et RLS du
catalogue; elles n’ajoutent volontairement pas les prix, preuves, signaux,
catégories ou feedbacks de vraies lignes. Les temps sont donc une baseline de
volume pour ce chemin synthétique, pas une promesse de latence de production.
