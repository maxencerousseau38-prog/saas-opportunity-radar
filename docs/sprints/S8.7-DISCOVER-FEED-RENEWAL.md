# S8.7 — Discover feed renewal (PD-41)

**Date:** 13 November 2026 · **Decision:** PD-41, instruction of the product
owner: "à chaque ouverture de la plateforme, la découverte doit être
renouvelée intelligemment : nouveaux SaaS en priorité, SaaS déjà consultés
moins souvent, sans répétitions inutiles", without breaking the pagination
or the favourites.

## Audit (before the change)

| Point | Observed |
|---|---|
| Default sort | `relevance`, which without a search is the catalogue arrival date (`first_discovered_at` descending) |
| Production data | All 8,540 visible SaaS arrived on 12 November 2026: the same order, the same first cards at every opening |
| Profile views | Recorded (`workspace_product_states.last_viewed_at`, members and above) but used by no ranking |
| Cards seen in the feed | Not recorded |
| Random order | Available as a sort (`random`), a new shuffle at each mount of the page, no memory of what was seen |
| Pagination | Keyset on (sort value, id), HMAC-signed cursor; the client already ignored a card received twice |

## What changed

1. **Rule `feed-1`** (`packages/domain/src/discover/feed-ranking.ts`,
   browser-safe entry `@sor/domain/feed`), mirrored by
   `private.feed_score` (pgTAP 030 asserts the same cases):

   | Situation of the product for the workspace | Score (draw ∈ [0, 1) per product and session) |
   |---|---|
   | Never shown, never opened | draw + 0.5 + 1.0 × fade(age in catalogue, 14 days) |
   | Shown in an earlier session, not opened | draw − 0.9 × fade(since shown, 7 days) − 0.08 × min(showings, 5) |
   | Profile opened before | draw − 0.4 − 1.2 × fade(since opened, 30 days) |

   fade(d, N) = max(0, 1 − d/N). The ranges overlap on purpose: a product
   seen long ago comes back, less often than one never seen. A text search
   keeps its relevance first (the feed order only breaks ties).
2. **Feed session**: one per opening of the platform (new tab or app launch,
   or after 30 minutes of inactivity; `sessionStorage`). The server assigns
   its start and returns it with each page; the signed cursor carries it.
   Signals recorded during a session only count from the next one, so a
   session's order never moves: pages stay consistent and coming back from a
   profile shows the same feed.
3. **Signals** (`workspace_feed_signals`, migration
   `20261129090001_discover_feed_renewal.sql`): a card counts as shown when
   at least 60 % of it is on screen; a profile counts as opened when tapped
   from the feed (profile views from elsewhere still count, through
   `last_viewed_at`). Sent in batches every 4 s and when the page is hidden,
   to `POST /api/v1/workspaces/{id}/feed/signals` (member and above), which
   calls the server-only RPC `sor_record_feed_signals` (role checked again,
   visible products only, each card once per session). Members read the
   table; nobody writes it from the browser. Viewers browse a renewed feed
   too but record nothing (as for profile views).
4. **Discover**: "Pour vous" is the default and first sort; saved searches
   keep their own sort. `catalog_search_v3` adds the session start; v2 stays
   for the web app deployed during the rollout.

Unchanged: favourites, hidden products, statuses, collections, filters,
count, the other sorts, the visibility and exclusion rules.

## Verification

- `@sor/domain` unit tests (score cases, session renewal, server-side
  session start), web cursor test.
- pgTAP 030 (36 assertions): privileges and RLS, write path (viewer and
  non-member refused, old sessions refused, at most 100 cards per call,
  excluded products never recorded), parity with `@sor/domain`, ranking
  (recent addition first, cards seen and opened after the never-seen ones),
  pagination consistent while signals are recorded between pages, same feed
  when coming back in the session, next session renewed, favourites
  untouched, text search, workspace isolation. pgTAP 019 manifest updated.
- Playwright (real catalogue step): default "Pour vous", same order after a
  reload, more pages without any duplicate, signals recorded, a new opening
  shows none of the cards already seen, the favourite survives.
- Local timing on 8,550 real products as a member: first page 0.29 s with
  "Pour vous" versus 0.25 s with the previous default.

## Not done

- No popularity, no AI and no cross-workspace signal: the ranking only uses
  the workspace's own history and the catalogue date.

## Follow-up: catalog_search_v2 dropped (13 November 2026)

At the product owner's request, once PR #18 was deployed:
`20261130090001_drop_catalog_search_v2.sql` drops the function (no object
depended on it, no code called it). pgTAP 023 and 026 and the CI timing step
now use `catalog_search_v3` (the timing step measures the default
"Pour vous" sort). Rolling the web app back to a deployment older than
PR #18 would now fail on search: roll the database forward instead.
