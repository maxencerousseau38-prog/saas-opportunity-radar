# S8.6 — Site visuals and visual quality (PD-40)

**Date:** 13 November 2026 · **Decision:** PD-40 (amendment of ADR-016),
instruction of the product owner: "chaque SaaS doit être représenté par son
véritable univers visuel" — official hero first, then an authentic interface
screenshot, then the Open Graph image; never a random, generic or unrelated
image; an elegant fallback otherwise.

## Audit (production, 13 November 2026, read-only)

| Measure | Value |
|---|---|
| Visible SaaS | 8,540 |
| With a visual | 5,005 (59 %) |
| By kind | 4,986 publisher share images, 24 free-licence (Commons) images, 0 hero, 0 screenshot |
| Images shared by several products | 8 images on 22 products (e.g. Lovable's default preview on 7 unrelated products, Softr's default, one site's template on 3 others) |
| Width | 4,762 ≥ 1,200 px, 198 between 800 and 1,199, 50 under 800 |
| Shape | 4,868 between 1.3:1 and 2.1:1, 112 wider, 30 narrower |

In the committed share-image snapshot (5,321 references): 88 App Store icon
cards (`mzstatic.com …/1200x630wa`, the app icon on a blurred background), 4
Chrome Web Store default images, 261 files named `…default…` (mostly a site's
own branded default, kept unless shared), 422 images on a CDN other than the
page's host (Framer, Webflow, Cloudinary…: the page's own assets).

Root causes: only one automatic kind looked at the product's site, and it
took the link-preview image without asking whether it showed the product.

## What changed

1. **Site visuals** (`@sor/data-sources/site-images.ts`, `share-image.ts`):
   the same visit of the official home page now also lists the hero and
   interface-screenshot candidates the page shows, each only with an explicit
   signal (see ADR-016, PD-40), and checks up to three of them.
2. **Rules `visref-2`** (`@sor/domain`): minimum size per kind, shape,
   near-blank detection, platform defaults, stock photos, cross-product
   duplicates (`dropSharedImages`).
3. **Database** (`20261126090001_site_visual_references.sql`, then
   `20261127090001_site_visual_references_same_image.sql`, pgTAP 029):
   the two reference kinds, one precedence (`private.visual_rank`), automatic
   primary hand-over (`private.refresh_primary_visual` + trigger), and
   `sor_retire_generic_visual_references()`.
4. **Collection**: `visuals.js collect official <publisher.json> <site.json>`
   in the *Catalog visuals* workflow (one visit per official site);
   `visuals.js ingest` loads the snapshots then retires generic references.
5. **Display** (`apps/web/lib/visuals.ts`): honest label and rights note per
   kind; screenshots cropped from the top (interface header and main view),
   others centred; profile shows the image whole at its own ratio; skeleton,
   fade-in, `fetchpriority=high` on the first cards and on the profile image,
   lazy loading elsewhere; broken references fall back to the monogram card.

## Validation before collection

Static extraction on 110 random catalog home pages (fetched for review only):
the kept candidates were real product views (schema editors, finance
dashboards, app screens, named heroes); two false-positive patterns found and
fixed before collection (`object-cover` utility classes read as a hero,
"analytics" in an alt text that described a Google Analytics chart). Pages
rendered only by JavaScript expose no image in their HTML: they keep their
share image (no headless browser, by design).

## Collection (13 November 2026, *Catalog visuals* run 3)

9,175 listings, one visit per official site:

| Snapshot | References | Main refusals |
|---|---|---|
| `site.json` | **941** (670 interface screenshots, 271 heroes) | no hero/screenshot signal in the static HTML 5,670; too small 508; robots.txt 381; near-blank 150; decorative hero (people, scenes, stock) 327 |
| `publisher.json` | 5,123 share images (5,321 before visref-2) | no share image 1,378; platform defaults 102 (App Store icon cards, builder previews); near-blank 52 |
| `licensed.json` | 27 free-licence images | unchanged |

Visual review of random samples: the screenshots are real product
interfaces; the first hero sample still contained lifestyle and stock photos
(a man with a coffee, a portrait, a sky, an event collage), hence the
relevance rule `heroShowsProduct` (`@sor/domain/discover/visual-relevance.ts`):
a hero is kept only when its alternative text or file name names the product
or describes a view of it, and never when it describes people, places or
stock photography. Applied offline to the snapshot (`visuals.js refine`) and,
for later collections, in the collector before any download.

Run 4 (same day, relevance rule inside the collector, so a decorative hero
gives way to the next candidate, often a screenshot): **1,001 site visuals
(715 interface screenshots, 286 heroes)**, 588 decorative heroes refused;
5,139 share images; 27 free-licence images. These are the committed
snapshots loaded into production.

## Not done

- No headless-browser screenshots, no generated images, no copies.
- No periodic revalidation job yet (a broken reference already falls back on
  the card and the profile; a reload of the snapshots replaces stale ones).
